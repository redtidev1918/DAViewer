# 登录状态：现状审查与实施建议

日期：2026-10-16。基于 main 的 97f3282；仅方案，不代表功能已实现。

## 结论

复用现有 WebSessionStatusController 作为网页登录的唯一认证裁决者，WebSessionCoordinator
负责触发；新增设置页与只读展示模型。不要再创建能独立验证或改写登录结论的
SessionHealthService。官方 API 授权、网页登录、推荐功能可用性分别表达。

## 已有能力与缺口

| 项目 | 当前实现 | 需要补充 |
| --- | --- | --- |
| 身份验证 | HTTP 首页验证；不确定或匿名结果按规则升级真实浏览器复核 | 展示证据来源、时间和明确原因 |
| 并发保护 | 在途合并、账号 epoch、generation、凭据版本保护 | 手动检查的可观察进行中状态 |
| 频率控制 | 每分钟调度；健康缓存 5 分钟；失败退避 30 秒/2 分钟/10 分钟；恢复前台请求强制检查 | 改为按需、按时间门槛调度；保留错误事件触发 |
| Cookie 恢复 | 仅补齐缺失且未过期条目；串行写入；读回身份；日志记录失败 | 结构化恢复结果，不能把本地读回叫作服务端认证成功 |
| 历史 | lastCheckedAt 只在成功时写入；降级后的状态对象不保留该字段 | 最近尝试、最近成功、当前结果分别保存 |
| 用户入口 | 设置页账号信息、原始 Cookie 查看/导入/导出；登录入口 | 独立“登录状态”页，原始 Cookie 入口移入高级区 |
| 提醒 | 全局可关闭提示；恢复健康后清除关闭记录 | 明确区分未登录、已失效、挑战锁定；按账号/事件去重 |

注意：每分钟调度不等于每分钟发网络请求，实际受缓存、退避、登录条件限制。
当前 needsLogin 包含 locked；locked 表示挑战限制，不能在新页面显示为 Cookie 失效。

## P1：可观察状态和手动恢复

新增 `/settings/login-status`。页面显示当前账号、网页登录状态、最近检查时间、
最近成功验证时间、功能影响说明，以及“检查登录状态”“打开登录页”。
官方 API 授权单独显示；其本地 signedIn 不能标作刚刚经服务器验证。

两种登录各自维护当前状态、最近检查时间、最近成功验证时间、失败类型及恢复操作，
不能共享一个验证时间或用一方成功覆盖另一方异常。官方 API 状态复用现有 OAuth
控制器与可信身份请求结果，网页登录状态复用现有 WebSessionStatusController。
缺乏服务端证据时显示“尚未验证”，不得用本地令牌存在代替验证成功。

| 页面卡片 | 手动操作 | 异常影响说明 |
| --- | --- | --- |
| 网页登录 | 检查网页登录；打开网页登录/验证入口 | 说明推荐等依赖网页登录的功能可能受影响 |
| 官方 API 登录 | 检查 API 登录；重新授权 | 说明关注、通知、收藏等依赖官方 API 的功能可能受影响 |

实现前核对各功能的实际通道依赖，避免把混合依赖功能概括为全部可用或全部不可用。
两种恢复操作入口独立，复用已有流程；如现有流程必须联动，先明确说明影响范围，
不得静默清除另一种登录。P1 不为实现入口独立而重写认证流程。

显示模型采用两个维度，避免恢复故障覆盖真实身份结果：

- 身份：待检查、已验证登录、未登录/需要重新登录、暂时无法确认、需要完成网页验证。
- 本地存储：未检查、已保存、恢复中、已读回、恢复异常。

没有登录历史的 anonymous 显示“未登录”；曾登录且被可靠证据否定才显示“需要重新登录”。
locked 显示“网页验证受限”，提示等待或调整网络，提供打开网页验证入口。
即便当前身份已验证，持久化失败也单独提示“本次可用，下次启动可能需要重新登录”。

在现有状态链补充 `isChecking`、`lastAttemptAt`、`lastSuccessAt`、`reason`、
`evidenceSource`；恢复控制器提供结构化 `RestoreResult`。不从日志反推界面状态。
按账号持久化最近成功时间等非敏感历史；冷启动只显示“上次验证成功”，不能直接恢复 healthy。
登出、换账号和旧异步结果必须遵守现有 epoch/generation 规则。

手动检查仍调用现有 check，合并在途请求，按钮显示进度并禁用重复点击。
允许用户越过普通缓存，但不能无条件绕过挑战锁定和频繁操作保护。
完成后显示本次检查结果；不能仅因保留旧 healthy lease 就声称本次检查成功。
重新登录复用 `/web-login`；不要预先清 Cookie 或退出 OAuth。

## P2：低频、事件驱动检查

将频率策略放在现有 Coordinator，使用可注入时钟测试：

1. 启动：有历史网页登录且距成功验证超过 24 小时，进行一次检查；恢复失败/凭据变化
   等新证据另行触发。24 小时是调度阈值，不是身份可信期限。
2. 回前台：距成功验证超过 6 小时，且正在使用需要网页登录的功能时检查。
3. 认证相关响应、登录完成、导入完成：汇入同一验证入口。网络/403 只触发验证或
   暂时不可用；不能直接清会话或判定失效。
4. 连续前台使用：进入认证功能时检查到期时间；必要时用单次到期任务覆盖长时间停留，
   后台暂停。不再每分钟轮询。

先核对推荐流对现有 5 分钟健康缓存的依赖，避免把调度间隔直接当作授权有效期。
同一凭据、同一账号的重复信号合并；失败退避保留；显式锁定停止自动重试。
现有网络结果只有在携带可信身份和当前凭据关联证据时才能更新健康结论，普通 HTTP 200 不算。

## P3：提醒和引导

复用 AppNoticeHost，不新增第二套横幅。明确失效才提示重新登录；未知状态在设置页说明，
需要时在受影响功能处显示“暂时无法确认”。挑战锁定使用不同文案和操作。
一次故障一个提醒，关闭后跨页面保持；成功恢复后才允许下一事件重新提醒。
建议将关闭记录绑定账号和故障事件，避免重启反复提示或串号。

## 验收

| 阶段 | 交付内容 | 验收重点 |
| --- | --- | --- |
| P1 | 双登录状态页、独立验证历史、手动检查、Cookie 恢复结果 | 不改变现有认证裁决、自动恢复与调度行为；仅增加观察结果及用户主动入口 |
| P2 | 低频按需检查、去重、缓存与退避优化 | 不增加误判；验证 RFY 首次加载、分页、刷新、恢复后的请求数量与归属不退化 |
| P3 | 登录失效提醒与重新登录引导 | 403、挑战受限、网络错误不误报为登出；提醒和恢复操作明确对应受影响通道 |

- 断网、超时、普通 403、挑战页面均不清 Cookie、不退出 OAuth、不误报失效。
- 双通道一正常一异常时，分别显示状态、时间和操作；一次检查不得覆盖另一通道历史。
- 已验证身份、历史成功、当前检查失败可同时正确展示。
- 无登录历史不弹“已失效”；锁定不要求反复登录。
- 连点检查、前后台切换和接口错误并发只形成一条验证链；旧账号结果不能污染新账号。
- Cookie 写失败、读失败、无恢复需求、持久化失败分别显示；成功读回不等于服务端接受。
- 用可控时钟验证 24/6 小时边界、失败退避和后台暂停。
- Android 与桌面分别验证恢复/读回/重启/切号；真实保留账号验证需独立设备证据。
- 如需更改外部响应解析，先取得新的真实捕获或权威规范并记录来源；不凭实现编造 fixture。

建议拆三次交付：P1 展示与手动操作 → P2 调度调整 → P3 提醒细化。
先完成 P1，保留现有恢复链和调度行为，降低回归范围。
